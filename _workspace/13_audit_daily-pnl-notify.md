## §3 M-1 · 전송 창 경계 — 실측 근거 있는 요구사항 미충족 경로

### 사실
- 창은 15:30:00.000 **포함**까지 → 15:29 발화 시 예산 **60초** (`MarketCalendarService:28,66-71`)
- 스케줄 스레드는 **1개** (`pool.size` 미설정 → Boot 기본 1. 로그 `[scheduling-1]` 1042건 / `scheduling-2` **0건**)
- 그 1개를 `@Scheduled` **14개**가 공유 (1초 주기 4종 포함)
- KIS 호출은 초당 1건 직렬화, read timeout **10초**

### 같은 스레드 15:25 크론(`RunStreakRecorder:52`) 발화 지연 실측

| 날짜 | 실제 발화 | 지연 | 그날 |
|---|---|---|---|
| 09-10 / 09-11 | 15:25:00.2 / .7 | +0.2초 / +0.7초 | 정지 상태(할 일 없음) |
| 09-02 | 15:25:12.6 | **+12.6초** | 타임컷 5종목 |
| 09-01 | 15:25:24.1 | **+24.1초** | 타임컷 5종목 |
| 08-31 | 15:25:35.0 | **+35.0초** | 타임컷 5종목 |
| **09-08** | **15:30:21.6** | **+321.6초** | 잔고 API 연속 timeout |

→ **6일 중 4일이 12초 이상, 1일(17%)은 15:30을 통째로 넘겼다.**
→ 지연 0초대인 이틀은 전부 즉시 return한 날이다. **할 일이 있는 날만 늦는다** — 손익 리포트가
가장 의미 있는 날이 정확히 그런 날이다.

09-08 상세: 15:00~15:29 내내 `잔고 API 실패 … Read timed out` 연속 → **15:15 타임컷이
15:29:40에 발화**해 15:30:16까지 스레드를 점유. 그날 15:29 작업은 `:85` 게이트에서
**원장도 알림도 둘 다 무산**됐을 것이다.

### 왜 알림이 원장보다 더 위험한가
`isDuringMarketHoursNow()`가 **두 번**, 다른 시각에 평가된다:
`DailyPnlRecorder:85`(잔고 조회 전) → `fetchBalance()`(레이트리밋 ≥1초 + HTTP 최대 10초) →
`TelegramNotifier:52`(전송 직전). ①을 15:29:58에 통과해도 조회가 3초 걸리면 ②는 탈락 →
**원장은 기록되고 알림만 사라진다.**

그 소실은 예외가 아니라 **조용한 skip**(`TelegramNotifier:53` log.info)이라 `notifyClose`의
catch가 못 잡고 **경고조차 안 남는다**. 재시도도 없다 — 크론은 하루 1회이고 `isClosed()`가
true라 재실행은 `:96-98`에서 조기 return.

→ 코드 주석 `:125` "15:29은 텔레그램 전송 창 안이다"는 **예약 시각 기준으로는 참**이지만
**실제 발화 기준으로는 실측 6일 중 1일이 반례**다.

**심각도 MEDIUM 근거**: 돈이 새지 않고 안전장치도 무력화하지 않는다. 그러나 "매일 마감 손익을
알려달라"는 요구를 **조용히 못 지키는 경로가 실측으로 존재하고 사용자가 알 방법이 없다.**
