# Phase 1.3 — 체결 추적 근본 수정 (설계 + 월요일 진단 런북)

> 로드맵 Phase 1.3 (`~/.claude/plans/whimsical-waddling-whistle.md`). 지금은 설계만.
> **실제 수정·진단은 월요일 장중(살아있는 체결)에 수행.** 이 노트를 이어받아 진행한다.

## 확정된 문제 (이번 세션 진단 증거)
- `FillProcessor.inquireFill`(TR `VTTC8001R`, `inquire-daily-ccld`, **주문번호 ODNO로 조회**)가
  **실제 체결된 주문에도 빈 응답**을 준다:
  `rt_cd=0` · `msg="모의투자 조회할 내역(자료)이 없습니다"` · `output1=[]`.
  (2026-07-28~30 진단: 659·671·19201·19224 등 — 증권사엔 보유/체결이 있는데 조회는 0.)
- 앱은 "빈 output1 = 미체결(0)"로 해석 → 포지션 미생성 → 유령 desync.
- 현재는 **완화책**으로만 복구: 타임아웃(10분) 취소가 "취소할 수량 없음/원주문번호 없음"
  (NO_OPEN_QTY)으로 거부되면 `reconcileFilledFromBalance`가 실잔고로 대사(e1e095d).
  즉 **뿌리(조회가 체결을 놓침)는 미해결**, ~10분 지연 + 레이트리밋 시 더 지연.
- 손댈 파일: `src/main/java/com/trading/order/FillProcessor.java`(inquireFill, 약 136~185행).

## 유력 가설 (월요일에 검증)
1. **ODNO 필터 문제**: ODNO 없이(당일 전체 체결) 조회하면 체결이 보이는지. 보이면 ODNO
   매칭이 원인.
2. **주문번호 불일치**: 주문 접수 응답의 ODNO(저장값) vs 체결내역의 ODNO(KRX 전송주문번호 등)가
   다를 가능성. 저장 ODNO로 조회하니 매칭 실패 → 빈 결과.
3. **파라미터**: `CCLD_DVSN`(00 전체 vs 01 체결), `INQR_DVSN`, `SLL_BUY_DVSN_CD` 등을 KIS 공식
   VTTC8001R 샘플과 대조. 현재 코드는 CCLD_DVSN="00", SLL_BUY_DVSN_CD="00".
4. **모의 환경 한정 결함**: 위 무엇도 아니면 모의 API가 원래 이런 것 → 실전에선 정상일 가능성.

## 월요일 진단 절차 (런북)
1. 장중 앱이 어떤 종목을 매수·체결하면(대시보드/로그로 확인), 그 **fresh 주문**을 대상으로:
   - `FillProcessor.inquireFill`에 임시 진단 로그 재삽입(이전 세션 방식: 조회ODNO·응답odno·
     tot_ccld_qty·output1건수·rt_cd·msg 캡처). 커밋하지 말고 진단 후 제거.
   - 같은 주문번호로 **ODNO 유·무 두 가지 조회**를 나란히 찍어 비교(가설 1·2).
2. 원본 응답으로 가설 1~4 중 어느 것인지 확정.
3. 확정에 따라 아래 수정 택1.

## 수정 후보 (진단 결과에 따라 택1)
- **A. 조회 교정(선호)**: ODNO 사용/파라미터를 바로잡아 체결을 즉시 잡는다 → 유령 창 자체가
  사라짐(10분 지연 제거).
- **B. 모의 한정이면**: 뿌리 수정 불가 → 1.2 주기적 재동기화 + 실전 체결보고로 커버됨을 문서화,
  완화책을 정식 안전망으로 승격 명시. (실전 전환 시 재확인.)
- **C. 대안 엔드포인트**: 잔고 델타/실시간 체결통보(websocket)로 체결 확인 — 큰 변경, 최후 수단.

## 검증 (월요일)
- 수정 후: 매수 체결이 **다음 폴 주기(수초) 내에 DB 포지션으로 반영**(현재는 ~10분).
- Red-Green: 수정 있으면 fresh 체결 즉시 추적, 되돌리면 다시 놓침.
- `spring-build-verify`로 전체 테스트(현재 424) + 종료 코드 0, 매매코드라 `risk-rule-audit` 병행.

- 흐름 고정·프로필 격리·TDD·실제 주문은 사람 게이트.
