# 37_audit — paper 누적 낙폭 한도 10% → 8% 적용 전 감사 (`PUT /api/params {"risk.mddLimit":"0.08"}`)

> 2026-10-10(토) · risk-auditor · 코드·파일 수정 0 · gradle 0 · H2 접속 0 · 실행 중인 앱에 읽기 전용 GET 4회.
> 리더가 에이전트 보고 전문을 이 경로에 보존했다. 적용 결과는 `38_ops_mdd-guard-8pct.md`.

**CRITICAL 0 · HIGH 0 · MEDIUM 3 · LOW 4 → 적용 가능 (조건 5개, 맨 아래)**

계획대로 `"0.08"`을 한 번 보내면 신규 매수 차단과 강제청산이 함께 즉시 8%로 바뀐다. 오늘(토요일)은 아무것도 발동하지 않고,
백테스트는 10% 그대로다. 적용을 막는 문제는 없다. 다만 이 값은 git 밖(운영 DB `app_setting`의 한 줄)에만 남는다.
"기본값 원복" 버튼 한 번, 또는 DB 교체·복원만으로 조용히 10%로 돌아간다. 그래서 30_audit M-4는 "해소"가 아니라
"부분 해소(런타임만)"로 남겨야 한다.

**쉬운 말로(사용자 전달용)**: "통장이 최고 기록보다 10% 줄면 자동으로 멈추는 차단기"를 8%로 더 예민하게 맞추는 일이다.
이미 3.3% 빠져 있어서, 앞으로 약 47만원을 더 잃으면 멈춘다(지금은 약 68만원). 이 다이얼은 프로그램 코드가 아니라 설정
저장소에 적힌다. 그래서 설정 화면에서 "기본값 원복"을 누르면 아무 알림 없이 10%로 돌아간다.

### 2. 백테스트 격리 — 10% 유지(이중 장벽)
1. **ApplicationReadyEvent가 오지 않는다.** `BacktestOrchestrator`는 CommandLineRunner(`:19`)이고 run() 안에서 `System.exit`(`:43`)한다.
   Spring Boot 3.3.5(`build.gradle:3`)는 started → callRunners → ready 순서로 진행하는데, ready에 닿기 전에 JVM이 끝난다.
   그래서 `loadOnStartup`(`TradingParamService.java:44`)은 백테스트에서 한 번도 돌지 않는다.
2. **backtest-db의 `app_setting`에 쓸 길이 없다.** 쓰는 곳은 `update/resetAll`(`:120-122,132`)뿐이고 HTTP로만 불린다. 백테스트는
   `web-application-type: none`(`application-backtest.yml:11`)이라 HTTP 서버가 없다. `schema.sql:106-111`은 테이블만 만든다. DB도 별도다.
3. 실험용 손잡이 `ExecutionKnobs.java:49-78`은 ATR 배수·1R·동시보유만 바꾸고 mddLimit은 건드리지 않는다. → 백테스트는 상수 0.10 그대로다.

### 3. PUT 경로 검증
- **값은 소수 `"0.08"`이 맞다.** `percent=true`는 화면 표시용일 뿐이다(`ParamCatalog.java:133`). 서버 허용 범위는 0.03~0.30(`:34`). scratch 재현:
  `"0.08"`·`"0.080"`·`" 0.08 "`·`"8e-2"` → 저장 / `"8"`·`"0.8"`·`"0.008"` → 거부("허용 범위 3% ~ 30%", `:197-203`), `"8%"` → 형식 오류.
  거부되면 메모리도 바뀌지 않는다(`TradingParamService.java:114-115`). 유일한 구멍이 M-2의 NaN이다.
- `crossValidate`(`:141-157`)는 일일손실 차단/청산 쌍과 트레일링 쌍만 비교하고, **mddLimit은 비교 대상이 아니다.**
- 성공 응답은 `{"saved":["risk.mddLimit"],"errors":{}}`, 로그는 `[Param] risk.mddLimit : 0.1 → 0.08`(`:125`)이다.
- 화면에서 바꾸는 경우: 설정 → "투자 파라미터" → "MDD 강제청산 한도" 칸이 10에서 8로(단위 %). 저장할 때 100으로 나눠 `"0.08"`을 보낸다
  (`core.js:249-254,349-360`). 힌트는 계속 "기본 10%"로 남는다(`:342-347`).
- 실측(GET): `/api/params`의 risk.mddLimit는 "0.1". 10-10 01:08 기동 로그에 `[Param]` 줄이 없으므로 `app_setting`은 지금 비어 있다. 이번 PUT이 첫 행이 된다.

### 4. 지속성과 함정, 대안과 비교
- 재시작: 유지된다(`loadOnStartup`, `:44-65`). 단 로그로는 확인할 수 없다(L-1).
- "기본값 원복": 10%로 돌아간다. DB를 새로 만들거나 복원해도 10%다. git에는 남지 않는다(`.gitignore:2`).

| 방식 | 반영 | git 기록 | 백테스트 앵커 | 원복 버튼 후 | DB 새로 만들면 | 비용 |
|---|---|---|---|---|---|---|
| A. 계획(PUT) | 즉시, 재시작 불필요 | 없음 | 영향 없음 | 10% | 10% | 코드 0 |
| B. yml 바인딩(커밋된 yml에 0.08, 백테스트는 0.10 고정) | 재시작 필요 | 있음 | 영향 없음 | 10%(재시작하면 yml 값으로 복귀) | 0.08 유지 | 2~3파일 + 테스트 |
| C. 상수를 0.08로 | 재시작 필요 | 있음 | **바뀜** → A/B 필요 | 8% | 8% | 1줄 + 앵커 재검증 |

권고: **지금 paper는 A로 적용해도 된다.** 실전(G2) 전에는 B 같은 정본화가 필수다. 주의 두 가지:
- `application-real.yml`은 `.gitignore:14` 대상이다. 거기 넣으면 또 git 밖이 된다. 커밋되는 공용 yml에 두고 백테스트 쪽 0.10을 명시해 고정하는 편이 낫다.
- B로 옮길 때 `app_setting`의 risk.mddLimit 행을 남겨두면, 이후 yml 변경을 DB 값이 이긴다(34_ops §2와 같은 함정).

### 5. 운영 위험 — 민감도

| | 10% | 8% |
|---|---|---|
| 자동 멈춤 선 | 9,079,925원 | 9,281,702원 |
| 남은 돈(9,755,825원 기준) | 675,900원(6.93%) | **474,123원(4.86%)** |
| A동 칸(400만원)이 잃어야 발동 | 16.9% ≈ 67.6R | 11.85% ≈ 47.4R |
| D0 최악(4.2% ≈ 16.8R) 대비 | 4.0배 | 2.8배 |
| 정지를 부르는 전고점 오염 크기 | +7.44% | **+5.11%** |

1R = 1만원. 실측 최대 시작자산은 10,088,806원(09-01)이고 ×1.15 = 상한 11,602,127원이다.

- **A동만 도는 지금, 8%에 실제로 닿는 길은 사실상 데이터 오염이다.** 시장 손실로 47R을 잃으려면 검증 최악의 2.8배가 필요하다 — ADR이 의도한 "검증 범위를 벗어나면 멈춘다"에 해당한다.
- 탐지선 평가: 텔레그램 알림은 사후 통지라 예방이 아니다. `isImplausible`의 15% 여유는 너무 넓어서 +5.11%~+15% 사이의 오염은 그대로 통과한다.
  새로 생긴 유효한 방어: 10-01부터 전고점 갱신은 장중에만 일어난다(`ShadowPortfolioTicker.java:9-13,33`). 관측된 오염 2건은 둘 다 장 밖이었으니 이제 구조적으로 막힌다. 남은 위험은 장중 오염이고, KIS 잔고 오독의 원인은 아직 조사되지 않았다.
- 개선 아이디어(BACKLOG감): 상한을 설정상 최대 노출(50%)이 아니라 실제 보유 노출로 계산한다. 그러면 보유가 0일 때는 오염이 원천 차단된다.
- 일일 손실 룰(−3%/−5%)과의 관계: 남은 거리 4.86%가 일일 −5%보다 작아졌다. 그래서 **하루에 −4.86%가 나면 MDD가 먼저 발동한다**(10%일 때는 일일 룰이 먼저였다). 일일 룰은 다음 날 기준이 새로 잡히고 MDD는 풀리지 않는다.

### 6. ADR 의도 대조
- ADR §2.2는 "MDD > 8%"라고 쓰고, §2.3에서 `triggerForceLiquidation()`을 "Global Equity Stop 전용"이라고 부른다. 즉 Global Equity Stop은 **강제청산 트리거**이고, 매수 차단만 따로 먼저 거는 2단계는 정의되어 있지 않다.
- 코드는 매수 차단(`GlobalEquityStopRule.java:40`)과 강제청산(`RiskMonitor.java:117`)이 **같은 값 하나**를 읽고 둘 다 `>`로 비교한다. ADR과 일치한다.
- 30_audit M-4의 "A동 −24%라야 발동"은 이미 빠진 3.3%를 빼먹은 계산이다. 정확한 값은 10%일 때 16.9%, 8%일 때 11.85%다.
- 슬리브 상한과의 관계: 슬리브 상한(A −12%/B −20%)은 그 칸만 멈추는 안쪽 방어선이고, 8%는 계좌 전체를 멈추는 바깥 방어선이다. 지금은 계좌 8% 가드가
  A동 약 −11.9%에서 걸려 A동 −12% 상한을 사실상 대신하지만, 결과는 계좌 전체 정지라 더 세다. **슬리브 상한 없이 B동을 다시 켜면, ADR이 경고한 "미검증 B동 때문에 A동까지 청산"이 더 빨리 온다.**

## 적용 조건 5개
1. 소수 문자열 하나만 보낸다(`{"risk.mddLimit":"0.08"}`). 응답이 `saved=[risk.mddLimit]`, `errors={}`인지 본다.
2. 바로 GET으로 확정한다 — `/api/params` value "0.08"(defaultValue "0.1" 그대로가 정상), `/api/performance/account` mddLimitPercent 8.0 · forcedStopThreshold 9281702 · roomToThreshold 474123, 로그 `[Param] risk.mddLimit : 0.1 → 0.08`.
3. 이후 **"기본값 원복" 버튼은 누르지 않는다.** 눌렀다면 0.08을 다시 PUT하고 재시작한다(트레일링 yml 값 복구 때문).
4. 다음 재시작 후 GET `/api/params`로 0.08이 남아 있는지 다시 본다. RiskMonitor의 "MDD 한도 10.0%" 로그는 무시한다. 이 확인 전에는 "지속 적용 완료"라고 쓰지 않는다.
5. 기록을 남긴다: "실효 0.08(app_setting, 10-10 적용) / 코드 기본·백테스트 0.10". 30_audit M-4는 **부분 해소(런타임만 · git 정본 없음 · 슬리브 상한 미구현)**로 두고 G2 선행 조건으로 유지한다.

실전 관련: 이번 변경은 실전 승격 근거가 아니다. `@Profile`에 real이 들어간 클래스가 0개라서 실전 프로필에는 MDD 가드 빈 자체가 없다 — 실전 전환 감사는 값보다 가드가 존재하는지부터 다시 봐야 한다.
코드 변경이 0줄이라 흐름·청산 상태머신·비밀키 감사 항목은 해당 없음이다.
