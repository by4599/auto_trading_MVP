# 운영 신뢰성 — 가용성 · 장애 대응 · 재가동 절차

> 전략이 아무리 좋아도 **시스템이 물리적으로 죽어 있으면 포지션은 무방비**다.
> 이 문서는 "앱이 살아있을 때의 규칙"(리스크 룰·거버넌스)이 아니라
> "앱이 죽었을 때, 죽으려 할 때, 다시 살릴 때"의 규칙을 정의한다.

비유하면 리스크 룰이 자동차의 브레이크라면, 이 문서는 **에어백과 견인 서비스**다.
브레이크는 운전 중에만 작동한다 — 시동이 꺼진 차에는 다른 종류의 안전장치가 필요하다.

---

## 1. 운영 환경 — 어디서 돌릴 것인가

| 환경 | 장점 | 리스크 | 판정 |
|---|---|---|---|
| 집 PC (현재) | 비용 0, 즉시 접근 | 절전/재부팅/정전/Windows 업데이트, 외출 중 대응 불가 | **모의투자 검증(Phase 1~2)까지만 허용** |
| 클라우드 VPS | 24/7 가동, 원격 접근 | 월 비용, 키 관리 부담 증가 | **실전 전환의 전제 조건** |

- 실전 전환 게이트에 "VPS 이전 완료"를 추가한다 (TRADING-RULES-AUDIT의 F-1~F-4와 동급).
- 집 PC로 모의 운영하는 동안에도: Windows 자동 업데이트 재부팅 시간대를 장외로 강제,
  절전 모드 해제, 장중 노트북 덮개 닫힘 방지 설정을 운영 체크리스트로 관리한다.

## 2. 데드맨 스위치 — 죽은 시스템은 자기가 죽었다고 알릴 수 없다

`TelegramNotifier`는 앱이 살아있을 때만 알림을 보낸다. 앱이 죽으면 알림이 "안 오는"
것이고, 사람은 무소식을 눈치채지 못한다. 따라서 **부재 감지는 반드시 외부에서** 한다:

```
앱 → (장중 5분마다 heartbeat ping) → 외부 감시 서비스 (healthchecks.io 등 무료)
외부 서비스: ping이 10분간 없으면 → 이메일/텔레그램으로 "시스템 침묵" 경고
```

- 하트비트에는 현재 모드(RUNNING 등)·보유 포지션 수를 포함해, 경고 수신 시
  "지금 시장에 노출된 게 있는가"를 폰에서 바로 판단할 수 있게 한다.
- 구현: `@Scheduled` 5분 주기 HTTP GET 1건 — Phase 2에서 half-day 작업량.

## 3. 크래시 후 재시작 — SAFE_MODE 기동 시퀀스

재시작한 앱은 자신이 죽어 있던 동안 무슨 일이 있었는지 모른다. 따라서 기동 직후
바로 매매를 재개하지 않고 아래 시퀀스를 강제한다:

```
기동 → ① KIS 잔고·미체결 주문 전체 조회 (브로커가 유일한 진실)
     → ② DB(Position/OrderHistory)와 대조 — Reconciler 즉시 1회 실행
     → ③ 불일치 시: 브로커 기준으로 DB 보정 + 보정 내역 텔레그램 보고
     → ④ 죽기 전 미체결 주문: 전량 취소 후 재평가 (죽어있던 동안의 시장 변화를
          모르는 채 낸 주문을 신뢰하지 않는다)
     → ⑤ 장중 재시작이면 SAFE_MODE로 대기 (신규 매수 금지, 보유 포지션의
          손절·타임컷만 활성) → 사람이 상태 확인 후 RUNNING 전환
     → ⑥ 장외 재시작이면 다음 개장 전 자동 RUNNING 복귀 허용
```

- `TradingMode`에 `SAFE_MODE` 추가 필요 (신규 매수 차단 + 방어 로직만 활성).
- ①~③은 기존 `ShadowPortfolioReconciler`를 기동 시 1회 강제 실행하는 것으로 재사용.

## 4. KIS API 운영 예외

| 상황 | 대응 |
|---|---|
| OAuth 토큰 만료 | 만료 전 자동 갱신. 갱신 **실패 시** 재시도 3회 후 SAFE_MODE 전환 + 알림 (시세를 못 보는 채로 매매하지 않는다) |
| 레이트리밋 | KIS는 초당 호출 수 제한이 있다 (모의/실전 상이 — 실측 확인 후 상수화). 호출부에 전역 rate limiter를 두고, 초과 시 해당 틱 스킵 (1초 루프는 한 틱 빠져도 무해) |
| 정기 점검 (심야) | 장외 시간이므로 무해하나, 점검 중 기동 시 토큰 발급 실패 → 재시도 백오프 |
| 응답 지연 | HTTP 타임아웃 명시 (현재 미설정 시 추가). 연속 N회 타임아웃 → SAFE_MODE + 알림 |

## 5. 장 운영 예외 — 캘린더와 이상 시세

### 5.1 거래일 캘린더

- KRX 휴장일(공휴일·연말 12/31 휴장)과 **수능일 1시간 지연 개장**은 하드코딩으로
  대응 불가. 연초에 KRX 캘린더를 설정 파일(`market-calendar.yml`)로 적재하고,
  `MarketCloseRule`의 15:20 등 모든 시각 상수를 "당일 장 마감 시각 기준 오프셋"으로 치환한다.
- 휴장일에는 루프 자체를 돌리지 않는다 (현재는 휴장일에도 API를 때린다 — 낭비 + 오동작 여지).

### 5.2 VI · 거래정지 · 상하한가

시장가 주문이 "항상 체결된다"는 가정은 한국 시장에서 세 가지 경우에 깨진다:

| 상황 | 증상 | 대응 |
|---|---|---|
| VI (변동성완화장치) | 2~10분 단일가 전환, 주문 지연 체결 | 주문 후 미체결 지속 → `FillPoller`가 이미 감지. VI 중 신규 진입은 금지 룰 추가 검토 (Phase 3) |
| 거래정지 | 주문 거부 | 주문 실패 예외 → 해당 종목 당일 매매 제외 + 알림 |
| **하한가 (강제청산 시)** | 시장가 매도 미체결 — **강제청산의 최악 시나리오** | `executeWithRetry` 3회 실패 → 수동확인필수 알림 (기존 동작 유지) + 런북 §7 절차로 대응. "청산 트리거 = 청산 완료"가 아님을 운영자가 인지 |

### 5.3 코퍼레이트 액션 (배당락·액면분할·증자)

- 발생 시 보유 수량·평단이 DB와 어긋난다. **탐지**: Reconciler가 브로커 잔고와
  수량 불일치를 발견하면 자동 보정하지 말고 **알림 + 수동 확인** (보정 공식이 액션
  유형마다 다르므로 v1에서는 사람이 처리).
- 예방: 워치리스트 종목의 권리락 일정(배당 기준일 등)을 주간 리포트에 포함 (Phase 3).
- v1(삼성전자 1주)에서는 실질 리스크가 낮으므로 멀티 종목 확장 전까지 탐지+알림만 구현.

## 6. 재가동 절차 — EMERGENCY_STOPPED에서 돌아오는 유일한 길

현재 `POST /api/trading/start`는 인증 없이 즉시 RUNNING 전환이 가능하다
([TradingController.java](../src/main/java/com/trading/control/TradingController.java)).
이는 두 가지 문제를 만든다: ① 강제청산의 "재가동 전까지 잠금"이 버튼 하나로 무력화되고
② `LiquidationService.phase`가 `FULL_LIQUIDATING`인 채 매매가 재개되는 상태 불일치.

**재가동 게이트 (구현 규칙):**

1. `EMERGENCY_STOPPED → RUNNING` 직접 전환을 **금지**한다. 허용 경로는
   `EMERGENCY_STOPPED → (재가동 게이트) → SAFE_MODE → RUNNING` 뿐이다.
2. 재가동 게이트 통과 조건:
   - [PERFORMANCE-GOVERNANCE §6](PERFORMANCE-GOVERNANCE.md)의 원인 진단 체크리스트 작성 완료 (4범주 중 판정 기록)
   - `LiquidationService.phase`를 IDLE로 리셋하는 **명시적 관리자 액션** (start와 별개 엔드포인트, 확인 문자열 요구)
   - 잔고 재동기화(§3의 ①~③) 완료
3. API 보안:
   - `server.address=127.0.0.1` 강제 (외부 접근 차단) — 모의 단계 즉시 적용
   - 실전 프로파일: 제어·설정 API에 관리 토큰 필수 + 시크릿키는 응답에 절대 미포함
   - VPS 이전 시: 방화벽 + SSH 터널로만 대시보드 접근

## 7. 런북 — 상황별 수동 대응 절차

| 상황 | 절차 |
|---|---|
| 🚨 강제청산 부분 실패 알림 | ① MTS/HTS 접속 → ② 잔여 보유 수동 시장가 매도 (하한가면 지정가 하한가 걸어두기) → ③ 청산 완료 확인 → ④ 앱은 EMERGENCY_STOPPED 유지 (재가동은 §6) |
| 🔇 데드맨 스위치 경고 (시스템 침묵) | ① MTS로 보유 포지션 확인 → ② 노출이 있으면 수동 손절선 주문 예약 → ③ 원격 접속으로 앱 상태 확인/재시작 (§3 시퀀스 자동 수행됨) |
| 📉 API 장애 중 보유 포지션 존재 | 시스템이 SAFE_MODE로 스스로 전환됨 → MTS에서 수동 관리로 전환, 복구 알림 후 §6 재가동 |
| 💾 DB 손상 | `position_rebuild.sql` + Reconciler로 브로커 기준 재구축 (기존 도구 활용) |

런북은 인쇄 가능한 1페이지로 유지하고, 반기마다 모의 훈련(강제청산 리허설)으로 검증한다.

**강제청산 리허설 명령** (모의계좌, 로컬에서만 접근 가능):

```cmd
curl -X POST localhost:8080/api/trading/liquidation-drill -H "Content-Type: application/json" -d "{\"confirm\":\"CONFIRM_LIQUIDATE\"}"
```

기대 순서: 미체결 일괄 취소 → 실잔고 조회 → 보유 전량 시장가 매도 → 텔레그램 결과 보고
→ EMERGENCY_STOPPED (재가동은 §6 절차). 장외 시간 실행 시 주문 거부가 "부분 실패 +
수동확인필수"로 보고되는지 확인하는 것도 유효한 훈련이다.

> ⚠️ **취소 범위 한계**: 청산 전 일괄 취소는 앱의 order_history에 기록된 주문만 대상이다.
> HTS/MTS에서 수동으로 낸 주문은 취소되지 않으므로, 청산 알림을 받으면 수동 주문 여부를
> HTS에서 함께 확인할 것.

### 7.1 리허설을 누가 실행하는가 — 역할 경계

| 주체 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 사람 | 리허설을 할지 결정, 예약을 켜고 날짜를 지정, 실전(real) 전환 승인 | — |
| 앱(예약 스케줄러) | 지정된 날짜·시각에 매수·청산을 **자동 실행** | 지정 없이 스스로 발동 |
| Claude(AI 조수) | 사전 점검, 설정·코드 작성, 실행 후 로그·잔고로 결과 검증, 문서 갱신 | **주문·청산 버튼을 대신 누르는 것** |

Claude는 사람 승인이 있어도 매매 실행을 대행하지 않는다. 사람이 그 시각에 자리에 없어
진행이 막히는 문제는 **대행이 아니라 예약(§7.2)으로 푼다** — 조작 권한의 경계를 흐리면
실전 전환 뒤에 사고가 난다.

### 7.2 예약 청산 리허설 — 사람이 자리에 없어도 훈련이 돌게

`application-paper.yml`의 `trading.drill`을 켜고 날짜를 지정하면, 앱이 그날 스스로 리허설을
수행한다. 기본은 꺼져 있고, **날짜를 콕 집지 않으면 절대 발동하지 않는다**(상시 반복 금지 —
리허설은 보유분을 전부 팔고 매매를 멈추는 조작이라 매일 돌면 매매 자체가 불가능하다).

```yaml
trading:
  drill:
    enabled: true
    date: "2026-08-20"   # 이 날짜에만 1회
    at: "10:00"          # 개시 시각
    deadline: "14:00"    # 이 시각까지는 못 했으면 다시 시도 (타임컷 15:15보다 앞)
    buy-if-flat: true    # 보유가 없으면 005930 10주를 먼저 사서 대상을 만든다
```

진행 방식: 개시 시각이 지나면 매 분 조건을 확인해서, 보유가 없으면 **매수만 접수하고 끝낸다**
(체결은 3초 주기 체결확인이 반영). 다음 분에 보유가 확인되면 그때 청산을 개시한다.
스레드를 붙잡고 기다리지 않으므로 체결이 늦어도 다음 틱이 이어받는다.

안전장치: 모의 프로필 전용 · 거래일에만 · 매수와 청산 각각 하루 1회 표시를 남겨 중복 발동 차단
· 실제 조작은 수동 실행과 **같은 관문**(`DrillService`)을 지나므로 리스크 룰이 막으면 그대로 멈춘다
· 단계마다 텔레그램 보고.

끝난 뒤 상태는 수동 리허설과 같다 — EMERGENCY_STOPPED이며 재가동은 §6 절차를 따른다.
**리허설이 끝난 날은 그 이후 매매가 멈춘다**는 뜻이므로, 날짜는 그래도 되는 날로 고른다.
