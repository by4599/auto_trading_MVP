# backtest-verdict — 백테스트 판정 절차

이 프로젝트의 원칙은 **"백테스트 없는 규칙은 채택하지 않는다"** 이다.
이 스킬의 목적은 좋은 결과를 만드는 것이 아니라, **나쁜 전략을 실전에 못 올리게
막는 것**이다. 기준을 낮춰 통과시키는 순간 이 시스템의 유일한 안전장치가 사라진다.

## 0. 시작 전에 읽는 것

| 파일 | 왜 |
|---|---|
| `docs/BACKTEST-DESIGN.md` §4 | 합격 기준의 원문 |
| 같은 문서 §7·§12·§13·§14 | 과거 판정 이력 — 이미 기각된 방식을 다시 제안하지 않기 위해 |
| `docs/BACKTEST-BASELINE-*.yml` | 현재 기준선 (있으면) |
| `docs/PERFORMANCE-GOVERNANCE.md` | 기준선 대비 괴리로 강등을 판정하는 규칙 |

## 1. 실행

빌드·실행 명령은 `.claude/skills/spring-build-verify/SKILL.md`를 따른다.

```
.\gradlew.bat bootRun --args="--spring.profiles.active=backtest --backtest.mode=<모드>"
```

| 모드 | 하는 일 |
|---|---|
| (없음/기본) | 변동성 돌파 워크포워드 + K 민감도 + 필터 A/B |
| `smoke` | 빠른 연기 테스트 (설정이 살아있는지만 확인) |
| `ma-breakout` | 이동평균 정배열 돌파 소급 검증 |
| `scalping` | 눌림목 반등 스캘핑 소급 검증 |
| `exit-lab` | 진입 고정, **출구(보유기간·트레일링)** 스윕 |
| `risk-lab` | 출구 고정, **사이징·동시보유 수** 스윕 |
| `events` | 공시 이벤트 유형별 D+N 반응 통계 |

주의: 방식이 섞이면 신호가 오염된다. 한 번에 하나의 전략만 켠다.

## 2. 합격 기준 — 5개 전부 통과해야 합격

| 지표 | 기준 | 왜 이 숫자인가 |
|---|---|---|
| 트레이드 수 | ≥ 100건 | 소표본은 운(運)이지 실력이 아니다 |
| Profit Factor | ≥ 1.3 (비용 차감 후) | 1.0 근처는 비용 오차만으로 뒤집힌다 |
| 기대값 | > 0 (**검증 구간만**) | 학습 구간 성과는 채점 대상이 아니다 |
| MDD (최대 낙폭) | ≤ 15% | 실전은 통상 이보다 나쁘다 |
| 민감도 | 인접 파라미터에서 PF ≥ 1.15 유지 | 뾰족한 최적점 = 과최적화의 지문 |

**하나라도 미달이면 불합격이다.** "PF는 훌륭한데 MDD만 아쉽다"는 합격이 아니다.

### 비용 가정을 낙관적으로 바꾸지 않는다

왕복 총비용(슬리피지+수수료+세금) **0.41%**가 현재 값이다. 이보다 낮추면
우상향 곡선이 만들어지지만 실전에서 우하향으로 뒤집힌다. 원칙은 하나다 —
**애매하면 항상 불리하게.**

## 3. 판정 보고 형식 (필수)

```
[백테스트 판정] MA 정배열 + 다일 트레일링 + 0.5R·동시5 (2026-07-22)
| 기준 | 값 | 통과 |
|---|---|---|
| 트레이드 수 ≥100 | 780건 | ✅ |
| PF ≥1.3 | 1.96 | ✅ |
| 검증구간 기대값 >0 | +1.30% | ✅ |
| MDD ≤15% | 9.9% | ✅ |
| 민감도 PF ≥1.15 | 1.41~1.96 | ✅ |
레짐 확인: 10개 창 중 8개 양(+) — 특정 장세 편중 아님
→ 판정: 합격
→ 남은 것: 왕복비용 민감도 · 분봉 정밀 · 약세장 스트레스
→ ⚠ 실전 승격은 아님 — 사람 게이트(G2) 승인이 반드시 선행
```

불합격 시에도 같은 표를 쓰고, 미달 항목에 ❌를 달고 **"불합격"이라고 명시**한다.
"아깝다", "거의 다 왔다" 같은 표현으로 흐리지 않는다.

## 4. 과최적화를 걸러내는 세 가지 습관

1. **검증 구간만 채점** — 파라미터는 학습 6개월에서 정하고, 성과는 검증 3개월에서만
   집계한다 (3개월씩 밀며 반복 = 워크포워드)
2. **파라미터를 흔들어 본다** — 핵심 파라미터를 ±20% 움직였을 때 성과가 급변하면
   기각. 좋은 전략은 최적점 근방이 완만하다
3. **레짐을 쪼개 본다** — 상승장에서만 벌었다면 그건 전략이 아니라 시장이다.
   창(window)별 손익 분포를 반드시 함께 본다

## 5. 필터·파라미터를 켤 때의 규칙

필터는 만들되 **기본 OFF**로 두고, 순정 대비 A/B로 이긴 것만 켠다.
채택 조건: 검증 구간의 **PF와 MDD 양쪽에서 우위**. 한쪽만 좋아지면 채택 보류하고
결과만 기록한다. 조합 탐색은 단일 필터 → 상위 2개 조합까지만 (조합 폭발 = 과최적화).

## 6. 합격 후에 하는 일

1. 기대값·PF·MDD·표본수·기간·파라미터를 `docs/BACKTEST-BASELINE-*.yml`로 기록
   — 이것이 나중에 "실전이 백테스트보다 얼마나 나쁜가"를 재는 분모가 된다
2. `docs/BACKTEST-DESIGN.md`에 새 절 번호로 판정 근거를 남긴다
3. **paper 기본값·리스크 룰·지갑 칸을 자동으로 바꾸지 않는다.** 변경은 사용자 승인
   사항이다
4. 실전 승격 사다리를 그대로 밝힌다: 백테스트 합격 → 모의투자 30건 이상 →
   축소 자금 실전. 각 단계마다 사람이 통과시킨다

## 7. 불합격일 때 하는 일

- 사유를 숫자로 적는다 (어느 기준에서 얼마나 미달인지)
- **기준을 낮추자는 제안을 하지 않는다.** 대신 무엇을 바꿔야 하는지를 제안한다
  (진입 로직 / 출구 로직 / 사이징 중 어디가 막혔는지)
- 과거 이력과 대조한다 — 같은 이유로 이미 기각된 방식이면 그 사실을 먼저 알린다

교훈: 진입만 바꿔서는 통과하지 못했다. 손익비(출구)와 리스크(사이징)를 함께
설계했을 때 처음으로 기준을 넘었다.
